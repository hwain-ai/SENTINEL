# SENTINEL 방향성·단순화 검토

현재 공개 범위는 Python·TypeScript·Java다. 하나의 명령과 언어별 독립 설치를 유지하고, 실제 호스트에서 설치부터 결과 확인까지 이어지는 경로를 검증한다.

이 문서는 2026-09-10 검토의 공통 원칙을 현재 공개 범위에 맞춰 정리한 것이다. 최신 구현·시험 결과는 [실행 계획](../exec-plans/active/2026-09-sentinel-unified-entry.md)을 따른다.

## 역할과 확인 경계

호스트 플러그인은 사용자의 검사 요청과 결과 설명을 맡는다. SENTINEL은 모듈 선택·도구 설치 확인·실행·취소·정리를 맡는다. 언어별 연결부는 기존 검사 도구 호출과 결과 변환을 맡는다. 언어별 빌드 로직을 공통 실행기에 모으지 않는다.

명령이 코드에 존재하는 것, 독립 설치 후 실행되는 것, Codex·Claude에서 실제로 호출되는 것은 각각 확인해야 한다. 검사하지 않은 결과나 설치 확인 성공을 프로젝트 품질 통과로 표시하지 않는다. 품질 실패와 도구 오류도 구분한다.

## 가능한 진행 순서

|방식|장점|후속 영향|
|---|---|---|
|결함 수정 뒤 작은 실제 프로젝트로 끝까지 검증|설정·검사·결과 해석의 오류를 좁은 범위에서 찾는다.|검증한 경로를 세 언어·두 호스트로 넓힐 수 있다.|
|호스트 설치부터 먼저 확인|플러그인 등록·스킬 발견의 문제를 빨리 찾는다.|실제 검사 오류는 별도 수정·재시험이 필요하다.|
|큰 공개 프로젝트 비교부터 반복|검사 범위와 실행 비용을 자세히 비교한다.|설치·기본 호출 문제 해결이 늦어질 수 있다.|

현재 작업은 첫 번째 순서로 진행한다. 다중 언어 설정과 미검사 인증 표시를 고친 뒤, 세 언어의 정상·품질 실패·변경 없음·도구 누락·취소를 시험하고 두 호스트 호출을 확인한다.

## 유지보수 원칙

- 기존 언어 도구, 버전 고정, 원본 보호와 실패를 그대로 드러내는 동작을 유지한다.
- 실행·정리 책임은 공통 실행기에서 관리하고 플러그인마다 중복하지 않는다.
- 새로운 검사 엔진·상주 관리 서비스·별도 서명 서비스는 필요가 확인됐을 때만 검토한다.
- 사용법에는 현재 가능한 동작을 쓰고 자세한 근거는 검증 기록으로 연결한다.

6개월 뒤 도구 갱신은 해당 언어의 버전 잠금과 호환성 시험에 한정돼야 한다. 새 연결이 실패하면 기존 설치를 유지하고 실패한 연결을 사용하지 않는다. 프로세스 종료는 파일·네트워크 격리를 보장하지 않으며, 부모 자체의 강제 종료 뒤 복구도 별도로 검증해야 한다.
