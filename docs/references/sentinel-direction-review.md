# SENTINEL 방향성·단순화 검토

결론: **하나의 명령과 언어별 독립 설치라는 방향은 맞다. 다만 준비·검증 작업을 넓히기 전에, Go 한 언어를 실제 통합 명령에서 끝까지 연결하도록 순서를 바꿔야 한다.**

목표·안전·유지보수를 맡은 서브에이전트 세 명의 독립 검토를 마쳤고, 주 담당자가 핵심 근거를 실제 코드·명세와 대조했다. 제품 코드를 수정하거나 기존 운영 승인 조건을 바꾼 문서는 아니다. 전체 다국어·호스트 플러그인 목표는 유지한다.

## 확인한 문제

|문제|근거|바꿀 진행 방식|
|---|---|---|
|준비된 기능이 사용자 명령으로 이어지지 않음|검토 당시 Go 실제 비교·빌드·격리 기록은 있었지만 실험용 통합 check는 일반 연결 프로그램만 호출했다. 기본 실행은 미승인으로 거부했다. [당시 연결 경계](../../docs/references/sentinel-native-connection-boundary.md#L13)|다음 완료 단위를 추가 준비물이 아니라 실제 Go 통합 실행으로 정한다.|
|실행·정리 책임과 시간 제한이 나뉨|부모는 연결 프로그램을 강제 종료하지만 Docker 호출은 별도 세션이다. 공통 기본 제한은 60초, Go 기본 제한은 900초다. [연결 공백](../../docs/references/sentinel-native-connection-boundary.md#L13)|기존 공통 실행기 한 곳이 생성·실행·정리와 전체 시간 예산을 맡는 방식을 우선 구체화한다.|
|사용법과 내부 검증 이력이 섞임|검토 당시 사용자 README에 내부 함수·여러 시점의 시험 이력이 함께 있었다. 해당 설명은 [개발자 참고](../../docs/references/sentinel-execution-api.md)로 분리했다.|사용 안내에는 지금 되는 것·설치·실행·안 되는 것을 두고 상세 근거는 참조 문서로 연결한다.|

부모가 정리를 맡아도 부모 자체가 강제 종료되는 모든 경우가 자동 해결되지는 않는다. 그 복구 조건은 별도로 검증한다. 새 상주 관리 프로그램을 추가하거나 기존 공개 요청 형식을 조용히 바꾸는 방식으로 해결하지 않는다.

## 의견이 갈린 부분

유지보수 검토는 컨테이너 없이 폐기 가능한 Go 복사본을 먼저 실행한 뒤 격리를 붙이는 순서를 추천했다. 추가 대조에서는 이것이 개발용 연결 시험일 뿐, 현재 승인된 실제 제품 경로의 완료는 아니라고 구분했다.

주 담당자는 이 중간 경로를 추가하지 않는 쪽을 추천한다. 이미 마련된 Go 격리 실행을 재사용하면 직접 실행과 격리 실행이라는 두 경로를 만들지 않아도 된다. 미인증이라는 표시는 파일·네트워크 접근을 막아 주지 않는다. [현재 입력·격리 조건](../../docs/exec-plans/active/2026-09-sentinel-unified-entry.md#L175)을 유지하면서 실제 통합 연결을 끝낸다.

## 단순화 기준

- **유지:** 기존 언어 도구 활용, 원본 복사본에서 검사, 버전 고정, 비밀값 보호, 파일·네트워크·자원 제한, 중단 뒤 정리, 실패를 성공으로 바꾸지 않기.
- **줄임:** 완료된 시험의 이유 없는 반복, 언어마다 별도 정리 기능, 같은 내용을 담는 검증 도구·기록 형식, 내부 용어와 지문 중심의 사용자 안내.
- **추가하지 않음:** 필요가 입증되지 않은 새 검사 엔진, 범용 플러그인 체계, 상주 관리 서비스, 새 서명 서비스.
- **작성 언어:** 새 프롬프트·설계·사용 안내·검토 보고서는 한글. 코드 식별자·명령·원본 실행 로그는 원문 보존. 과거 증거 전체를 번역하거나 다시 만드는 작업은 늘리지 않는다.

최종 사용 구조는 세 역할로 설명돼야 한다. 호스트 플러그인은 요청과 요약, SENTINEL은 선택·실행·정리, 언어 연결부는 기존 도구 호출과 결과 변환을 맡는다. 언어별 빌드 로직을 공통 실행기에 모으지 않는다.

## 선택지와 추천

|선택지|장점|대가|
|---|---|---|
|Go 한 언어부터 끝까지 연결|기존 실제 검증을 활용해 사용자 동작을 먼저 완성함|다른 언어는 이후 같은 구조로 순차 연결해야 함|
|여러 언어의 준비 체계를 먼저 완성|준비 기준을 넓게 맞출 수 있음|첫 실제 통합 사용이 계속 늦어지고 연결 오류의 수정 범위가 커짐|
|언어별 명령만 제공하고 통합을 미룸|개별 도구 제공에 집중할 수 있음|하나의 명령이라는 확정 목표를 바꾸므로 별도 사용자 선택 필요|

추천은 첫 번째다. 범위를 Go로 축소하는 것이 아니라 전체 목표를 끝내는 순서를 바꾸는 것이다.

## 다음 세 단계

1. 기존 통합 계약과 안전 조건을 보존하면서 부모의 정리 책임·시간 예산·실패 처리를 짧게 정한다. 이 범위의 내부 구현은 별도 사용자 선택 대기로 묶지 않는다. 공개 형식·기본 동작·보호 수준이 바뀐다면 별도 판단을 요청한다.
2. 사용자가 선택한 실제 Go 모듈을 설치된 통합 명령으로 검사하고 결과·취소·회수까지 연결한다. 고정 참조 프로젝트를 대신 실행하거나 품질 실패를 통과로 바꾸지 않는다.
3. Go의 정식 사용 조건을 검증한 뒤 해당 범위를 Codex·Claude Code에서 실제로 불러 확인한다. 다른 언어는 같은 실행 경계에 순차 연결한다. Java 최초 신뢰 판단은 Java에 한정하며 다른 언어 연결을 모두 막지 않는다.

6개월 뒤에도 실행·정리 코드는 한 곳에 있어야 한다. 도구 갱신은 바뀐 언어의 버전과 호환성 시험에 한정한다. 실패한 새 연결은 사용하지 않고 기존 설치·지문을 보존한다. 원본 보호나 정식 운영 허용 조건을 낮추는 변경은 별도 판단 대상이다.

## 검토 범위

이번 방향 검토는 코드·문서 대조다. 실제 프로젝트·Docker·플러그인을 새로 실행하지 않았으며 보안 감사나 Python 설치 보완본의 독립 승인을 대신하지 않는다.

명령이 코드에 있다는 사실과 사용자가 설치해 실제 프로젝트에서 쓸 수 있다는 사실도 구분한다. 언어별 README 정리에서는 이 둘을 섞어 지원 완료로 표시하지 않는다.
