# 언어 도구 설치 연결에 남은 실행·정리 경계

상태: 아래는 Go 통합 연결 전의 설계 검토 기록이다. 현재 구현 상태는 이 절과 [실제 Go 연결 기록](https://github.com/hwain-hwang/SENTINEL_GO/blob/main/docs/sentinel-go-native-validation.md)을 따른다. 플러그인 활성화 승인 문서는 아니다.

현재 결론(2026-09-10): 사용자는 A안인 통합 SENTINEL의 컨테이너 생성·시간 제한·직접 정리를 확정했다. Go의 설치된 통합 명령은 이미 이 구조로 실제 결과 반환·제한 실행·취소와 원본 보존·소유 컨테이너 0을 확인했다. 다른 언어도 같은 경계로 연결한다. Java 빌드 준비 및 Java·Python의 새 빌드·테스트 도구는 공식 Maven Central·PyPI 기반 최초 준비를 승인받았으므로 더 이상 사용자 답변 대기가 아니다. 상세 범위는 [승인된 설계](../../docs/design-docs/2026-09-sentinel-unified-entry.md)의 공식 배포처 준비 절을 따른다.

아래의 문제 분석·대안·다음 단계는 당시의 기록이다. 부모 SENTINEL 자체의 강제 종료 복구, 다른 언어 검증, 정식 운영 허용과 호스트 플러그인 활성화까지 완료됐다는 뜻은 아니다.

## 이미 가능한 범위

[제품 명세](../../docs/product-specs/2026-09-sentinel-unified-entry.md)는 정식 운영 승인 전에도 실험용 언어 도구를 허용한다. 따라서 새 서명 서비스나 정식 품질 인증을 먼저 만들어야만 연결 개발을 시작할 수 있다는 뜻은 아니다. 기본 check 실행 거부, 실험용 결과의 pass=false·certified=false, 미승인 호스트 플러그인 활성화 금지는 유지한다.

Go에서는 실제 native check와 상세 비교 실행을 구분한다. 상세 비교의 종료 0은 기록을 완성했다는 뜻이며, 프로젝트 품질 통과로 번역하지 않는다. 작은 연결 프로그램이 요청받은 module 대신 고정 공개 프로젝트를 몰래 실행해서도 안 된다. 선택한 module과 검사 복사본의 전체 입력 지문을 연결해야 한다.

## 소스에서 확인한 문제

1. [공통 실행기](../../src/sentinel/protocol.py)는 연결 프로그램을 별도 프로세스 그룹으로 시작하고, 시간 초과·취소·출력 초과 때 그 그룹을 강제 종료한다. 강제 종료인 SIGKILL은 종료 처리 코드를 실행할 기회를 주지 않는다.
2. 연결 프로그램 안에서 [GoSandbox](../../src/sentinel/go_sandbox.py)를 호출하면, 그 프로그램의 종료 처리에 있던 컨테이너 제거와 입력 재검사도 실행되지 않을 수 있다.
3. [컨테이너 실행기](../../src/sentinel/sandbox.py)는 Docker 명령마다 start_new_session=True를 사용한다. 그러므로 연결 프로그램의 그룹을 종료하는 것만으로 별도 그룹의 Docker 호출까지 끝났다고 볼 수 없다.
4. 부모가 소유권 식별값을 기억하고 한 번 조회하는 것만으로는, 아직 끝나지 않은 생성 작업이 나중에 컨테이너를 만드는 경우까지 해결되지 않는다. 생성이 끝났다는 확인과 정리 순서가 함께 필요하다.

이는 소스 구조에 근거한 연결 위험이다. 이번에 실제 컨테이너 누수나 공격 성공을 재현한 것은 아니며, 직접 GoSandbox를 실행해 보관한 과거의 정상 종료·회수 결과를 부정하는 것도 아니다.

시간 제한도 이어져야 한다. 현재 공통 명령의 기본 제한은 60초, Go 내부 실행의 최대 제한은 900초지만 공통 요청에는 이 시간 예산을 전달하는 항목이 없다. 사용자에게 무조건 제한을 늘리게 하는 것만으로 취소·강제 종료 문제가 해결되지는 않는다.

## 대안과 권고

|방식|장점|먼저 해결할 점|
|---|---|---|
|A. 부모 SENTINEL이 컨테이너 생성·실행·정리를 소유|연결 프로그램이 죽어도 생성과 정리를 맡은 주체가 살아 있다. 기존 공통 컨테이너 수명 관리 코드를 재사용할 수 있다.|언어별 입력·실행·응답을 부모의 수명 관리에 연결하는 명시적 native 계약이 필요하다. 기존 일반 bundle 계약을 조용히 바꾸지 않는다.|
|B. 자식 실행을 유지하고 부모에게 정리 책임 인계|기존 자식 요청·응답 구조와 가깝다.|생성 전 소유권 전달뿐 아니라 별도 Docker 호출·미완료 생성의 종료 확인까지 필요하다. 식별값 추가만으로 끝나지 않는다.|
|C. 별도 관리 프로그램이 감시·정리|검사 명령과 독립적으로 수명을 관리할 수 있다.|상주 프로그램 설치·감시·업그레이드·장애 복구가 추가된다. 현재 작업의 단순 연결보다 운영 범위가 크다.|

당시 권고는 A였다. B의 최소 내부 기능을 검토하다가 생성 작업 종료라는 선행 조건이 빠졌음을 확인해 구현을 보류했다. 그 검토 시점에는 새 제품 코드를 추가하지 않았고, 작성만 한 테스트 초안은 비공개 사본으로 보관한 뒤 제품 시험 목록에서 제외했다. RED 시험도 실행하지 않았으므로 TDD 완료로 세지 않는다.

## 다음 단계와 장기 영향

1. 기존 v1 bundle·요청·응답·기본 동작을 보존하면서 새 native 연결의 소유권과 시간 예산 계약을 구체화한다.
2. 생성 중·실행 중 연결 프로그램 종료, 정리 오류, 다음 module 실행 중단과 새 실행 복구를 검증한다. 정상 종료만 확인해서 연결 완료로 표시하지 않는다.
3. 선택한 실제 module과 고정 설치 입력이 같음을 검증하고, 기존 Go native check 결과를 공통 상태로 변환하는 실험용 도구를 연결한다. SDK 전체를 작은 bundle에 넣지 않는다.
4. 같은 경계를 다른 언어에 적용한 뒤 정식 운영 승인과 Codex·Claude Code 설치 플러그인으로 이어간다. Java 준비 도구의 최초 신뢰 선택은 이 문제와 별개다.

6개월 뒤에도 언어 엔진 교체는 해당 도구·SDK·의존성 지문과 호환성 시험에 한정되어야 한다. 부모가 수명을 소유하면 언어마다 별도 정리 프로그램을 유지할 필요를 줄일 수 있다. 실패한 새 연결은 사용하지 않고 기존 설치 지문과 실행 경로를 유지한다.

## 검증 기록

2026-09-09: Go 상세 비교의 독립 증거 검토는 Approved/Critical 0/Important 0/Minor 0이다. [실제 비교 기록](https://github.com/hwain-hwang/SENTINEL_GO/blob/main/docs/sentinel-go-native-validation.md)의 완료 범위는 유지한다. 이후 보류한 테스트 초안을 제품 목록에서 제외하고 원래 source·tests·README·패키지 파일의 바이트 일치를 확인했다. 새 전체 회귀 시험 259개는 12.049초에 통과했다. 이는 기존 코드 보존의 검증이지 새 회수 방식의 구현·검증이 아니다.
