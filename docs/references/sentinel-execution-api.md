# SENTINEL 실행 기반의 개발자 참고

사용자는 [통합 명령 사용 안내](../../README.md)를 먼저 읽는다. 이 문서는 실행기 구현을 확인할 때 필요한 내부 함수와 기존 검증 이력을 모은다. 실제 사용자 연결의 완료 범위는 사용 안내와 [실행 계획](../../docs/exec-plans/active/2026-09-sentinel-unified-entry.md)을 기준으로 확인한다.

## 격리 실행의 사전 준비: 개발용 API

[oci.py](../../src/sentinel/oci.py)는 로컬 Docker의 실행 파일·접속 소켓·버전을 확인하는 준비 코드입니다. 소켓은 Docker 서비스에 접속하는 로컬 통로입니다. 새 사용자 명령은 아니며 plan·doctor·기본 check는 호출하지 않습니다. Go 전용 실험 연결은 이 준비 함수를 호출합니다. 이 함수 자체의 성공은 실제 컨테이너 격리나 언어 품질 인증의 성공이 아닙니다.

|함수|입력|결과|
|---|---|---|
|prepare_session|승인 lock 파일 경로, 파일 원본 SHA-256, 새 기록 폴더 경로|Docker version만 조회하고 비공개 session.json의 SHA-256을 반환|
|recheck_session|동일 lock 경로·SHA-256, 기록 폴더, 앞서 받은 기록 SHA-256|기록과 현재 환경을 다시 대조. 성공해도 파일을 쓰거나 품질 승인을 하지 않음|

lock은 실행 환경의 승인값을 적은 JSON 파일입니다. 최상위 필드는 schemaVersion=sentinel-oci-executor-lock-v1, client, server, socket, image로 고정합니다. 호출자는 파일과 지문을 별도로 신뢰해야 하며 이 코드가 현재 머신을 자동 승인하지 않습니다. 정식 SPEC lock은 아직 배포하지 않습니다. 개발 검증용으로 기존 실행 계획의 승인값을 Git 밖에 옮긴 파일을 정식 정책 배포물로 취급하지 않습니다.

실행 대상은 /usr/bin/docker, 접속 대상은 unix:///run/docker.sock뿐입니다. 임의 Docker 명령을 받지 않으며 부모의 Docker 설정·인증·프록시 환경을 넘기지 않습니다. 소유자만 접근 가능한 빈 설정 폴더를 명시하고, 10초와 stdout·stderr 합계 1 MiB 제한에 기존 protocol의 process 수집·회수 코드를 재사용합니다. 이 공유 코드 변경 시 OCI 시험과 기존 실행 시험을 함께 실행해야 합니다.

기록 폴더는 Git 저장소 밖의 새 절대 경로이며, 바로 위 폴더는 현재 사용자 소유의 0700 권한이어야 합니다. 새 폴더는 0700, 기록은 0600으로 제한합니다. 각각 소유자만 접근하거나 읽고 쓸 수 있다는 뜻입니다. 실행 파일·소켓·폴더의 실제 신원과 버전을 대조하고 기존 기록은 덮어쓰지 않습니다. 파일 시각의 나노초 값은 정밀도를 잃지 않도록 십진 문자열로 기록합니다. 오류는 내부 경로·원본 출력을 담지 않은 ociPreflightFailed/종료 코드 5의 SentinelError로 반환합니다.

사용자가 지정한 경로와 자동 생성할 설정 폴더 경로에 같은 길이·제어문자 규칙을 적용하고, 게시할 기록도 재검증 때 쓰는 형식 검사로 먼저 확인합니다. 한글 경로는 허용합니다. 기록 내용·신원·파일과 폴더 동기화·마지막 경로 확인·기록 파일 닫기까지 마치면 게시가 완료됩니다. 그 전 오류나 취소에서는 이 작업이 만든 기록만 정리하며 다른 파일로 바뀐 기록은 삭제하지 않습니다. 게시 완료 후 마지막 읽기용 폴더 연결을 닫는 OS 오류나 취소는 이미 끝난 작업을 실패로 뒤집지 않고 기록 지문을 반환합니다. 버전 조회 중 취소는 실행을 정리한 뒤 호출자에게 다시 알립니다.

image 필드는 다음 단계에서 검증할 이미지의 지문을 보존할 뿐입니다. 이미지를 받거나 확인하거나 실행하지 않습니다. 실패한 비공개 기록 폴더는 자동 재사용·재귀 삭제하지 않고 새 경로에서 다시 시작합니다. 정식 연결에는 별도의 이미지·실행 환경·원본 보호·네트워크·자원 제한 검증이 필요합니다.

여러 작업을 이어 실행하는 호출자는 별도 취소 상태를 관리하고 다음 동작 전에 확인해야 합니다. 준비 작업의 완료 반환만으로 후속 컨테이너 실행까지 사용자가 계속 원한다고 판단하면 안 됩니다. Go 실험 연결도 이 규칙을 따릅니다. 이 API가 기록 저장과 호출자의 결과 수신을 모든 비동기 중단·프로세스 사망 시점에서 원자적으로 보장하는 것은 아닙니다.

검증 기록(2026-09-09): 기존 71개와 OCI 43개를 합한 114개 테스트, 새 설치본의 실제 로컬 Docker 버전 조회·기록 재검증, 파일 교체·저장 오류·연결 회수·완료 시점 전후 취소 시험을 통과했습니다. 독립 검토의 남은 지적은 없습니다. 이 검증에서 이미지나 컨테이너, 실제 언어 프로젝트는 실행하지 않았습니다.

## 고정 이미지의 격리 실행: 개발용 API

[oci_image.py](../../src/sentinel/oci_image.py)는 외부에서 받은 Ubuntu 이미지 manifest와 config의 원본 바이트를 검증합니다. manifest는 이미지 파일 목록과 지문을 담은 문서이고, config는 실행 환경 정보를 담은 문서입니다. 두 문서는 각각 최대 1 MiB이며, 고정된 전체 digest, Linux amd64, 허용된 OCI 또는 Docker schema 2 형식, config·layer 지문과 크기가 모두 이어져야 합니다. 이 함수는 네트워크를 사용하거나 이미지를 내려받지 않습니다.

[sandbox.py](../../src/sentinel/sandbox.py)의 Sandbox는 앞 절에서 준비한 lock·session과 검증된 이미지 문서를 받아 다음의 고정 순서만 실행합니다.

1. prepare_image는 전체 digest로 지정된 Ubuntu 이미지를 Linux amd64용으로 명시적으로 받고, 실제 image ID·저장소 digest·운영체제·CPU 구조를 다시 확인합니다.
2. run은 이미 준비된 image ID만 pull 없이 사용해 컨테이너를 생성합니다.
3. 생성 직후 시작하기 전에 이름·일회성 소유권 값·image ID·명령·환경·보안·자원 제한을 inspect 결과와 대조합니다.
4. 실행 결과는 종료 코드, timeout·OOM 여부, 출력 바이트 수와 SHA-256만 남깁니다. 원본 stdout·stderr와 Docker 오류는 공개 결과에 넣지 않습니다.
5. 성공·실패·timeout·취소에서 소유권을 확인한 정확한 컨테이너 ID만 삭제하고, 목록에서 사라졌음을 다시 확인합니다.

첫 profile은 host 경로를 전혀 mount하지 않습니다. network none, read-only root, 모든 capability 제거, no-new-privileges, UID/GID 65534, CPU 0.5개, 메모리 128 MiB, 추가 swap 0, PID 32개, 32 MiB /tmp만 허용합니다. Docker 명령 하나의 stdout·stderr 합계는 1 MiB, 사용자 실행 제한은 최대 60초입니다. 컨테이너 생성 결과에 ID가 있어도 생성한 이름·일회성 소유권 값·고정 이미지가 다시 일치하기 전에는 삭제 대상으로 신뢰하지 않습니다.

이 API는 새 사용자 CLI가 아니며 기본 check와 experimental check에도 아직 연결되지 않았습니다. 신뢰된 기존 Docker daemon을 사용한 제한된 profile일 뿐, VM 수준의 격리나 커널 취약점 방어를 보장하지 않습니다. 아래 Go 전용 profile이 별도로 네 입력 root를 연결하며, 이 기본 profile의 host mount 0개·UID 65534·최대 60초 계약은 유지합니다. 따라서 기본 profile의 성공만으로 Go·Java 등의 실제 지원이나 품질 통과를 주장하지 않습니다.

## 실행 입력의 독립 설치

[content_root.py](../../src/sentinel/content_root.py)는 도구 파일·의존성·프로젝트 복사본을 SHA-256으로 고정된 파일 목록과 대조해 독립 폴더에 설치합니다. 원본은 수정하지 않으며, 같은 내용은 재사용하고 다른 내용은 덮어쓰지 않습니다. 설치 파일은 소유자 읽기 전용, 실행 파일과 폴더는 소유자 읽기·실행만 허용합니다.

파일 누락·추가·변조, 링크, 검사 도중 경로 교체, 게시 실패와 취소를 검증했습니다. 2026-09-09 별도 검토 승인 후 관련 31개를 포함한 전체 186개 테스트가 통과했고 새 설치본과 소스가 일치했습니다. 현재 Linux x86_64에서 검증했으며 필요한 커널 기능이 없으면 설치를 거부합니다. 이는 실행 전 준비 기능이지, 실제 언어 빌드나 품질 인증의 완료가 아닙니다.

## Go의 독립 입력·격리 실행: 개발용 API

[go_runtime.py](../../src/sentinel/go_runtime.py)는 고정 Go SDK의 원래 지문을 검증하고, [go_inputs.py](../../src/sentinel/go_inputs.py)는 SDK·도구 실행 파일·오프라인 의존성·프로젝트 복사본을 네 개의 별도 설치 root로 조립합니다. root는 전체 파일 목록을 고정한 설치 폴더입니다. 도구를 다시 빌드할 때 SDK와 프로젝트를 함께 재설치할 필요가 없습니다.

[go_sandbox.py](../../src/sentinel/go_sandbox.py)의 GoSandbox는 이 입력들만 읽기 전용으로 연결합니다. 임의 host 경로·환경·사용자·Docker 옵션을 받지 않습니다. 사용자 UID/GID, CPU 2개, 메모리 2 GiB, 추가 swap 0, PID 128개, 열린 파일 1,024개와 제한된 임시 저장 공간을 실제 생성 설정과 대조한 뒤 실행합니다. 원본 Git 저장소는 연결하지 않습니다.

|요청|용도|
|---|---|
|preflight|다운로드를 끈 상태의 Go 의존성 확인|
|original|프로젝트의 원래 make 실행|
|help·doctor·crap·history|고정 native 실행기의 해당 명령 호출|
|mutation·check|명시된 생산 코드 목록으로 기존 native 검사 호출|
|comparison|go-mutesting의 제한된 비교 프로필 호출. 정식 품질 인증은 아님|

comparison·mutation·check 요청에는 선택 필드 mutant_timeout_ms를 지정할 수 있습니다. 변이 하나 때문에 나머지 검사가 계속 기다리는 일을 제한하는 값이며, 밀리초 단위 정수로 받습니다.

|요청|허용 범위|적용 대상|기존 전체 제한|
|---|---|---|---|
|comparison|1~840,000 ms|각 변이 재실행|840,000 ms(14분)|
|mutation·check|1~600,000 ms|각 변이 컴파일과 각 재실행에 각각 적용|600,000 ms(10분)|

원본 대조 테스트에는 이 선택 제한을 적용하지 않습니다. 컨테이너 제한은 최대 900초입니다. 전체 제한이나 취소가 먼저 발생하면 완성되지 않은 결과를 통과로 처리하지 않습니다. 변이가 제한 시간을 넘긴 결과인 timedOut도 killed(테스트가 변이를 잡아낸 결과)로 바꾸지 않습니다.

이 필드를 생략하면 기존 배포물에 보내던 명령을 유지합니다. 값을 지정할 때는 해당 요청의 --mutant-timeout-ms 옵션을 지원하는 고정 Go 배포물이 필요하며, SDK나 기존 도구 버전을 자동 교체하지 않습니다. 위 세 요청 이외의 명령에 지정하거나 boolean·문자열·범위 밖 숫자를 주면 Docker 실행 전에 거부합니다. 이 옵션은 개발용 API이며 통합 사용자 CLI에 새 옵션을 추가한 것은 아닙니다.

실행마다 새 작업 복사본을 만들고 입력 지문을 전후로 확인합니다. 성공·실패·취소 뒤 정확한 컨테이너를 제거하며, 취소와 제거 실패가 겹치면 실패를 숨기지 않습니다. 공용 관측에는 종료 상태·출력 크기·지문만 포함합니다. 시간 초과나 메모리 부족 시 native 결과가 정상적으로 수집됐다고 표시하지 않습니다.

이전 입력·격리 기반 검증(2026-09-09): 통합 실행기 216개 테스트와 재설치 source 대조, 관련 독립 후속 검토가 통과했습니다. 당시 go-multierror 1.1.1의 원래 빌드·doctor와 Go 전용 격리 시험 10종 및 다음 실행 복구를 확인했습니다. 정확한 artifact·실행 결과·검증 시점·한계는 [Go 실제 검증 기록](https://github.com/hwain-hwang/SENTINEL_GO/blob/main/docs/sentinel-go-native-validation.md)에 있습니다.

변이별 제한 연결의 후속 검증(같은 날): 전체 223개 테스트·재설치 source 대조·설치본의 연결 시험 6개와 독립 코드 검토가 통과했습니다. 이는 새 옵션의 연결 검증이며, 위 10종 실제 격리 시험을 새 배포물로 모두 재실행했다는 뜻은 아닙니다. 실제 비교 결과는 배포물 지문과 함께 별도 검증 기록에 추가합니다.

mutation·check 연결 확장의 소스 검증(같은 날): 관련 29개와 전체 230개 테스트가 통과했습니다. 이 수치는 명령 연결과 기존 기능의 회귀 검증이며, 확장 설치본의 실제 프로젝트 실행 결과를 뜻하지 않습니다.

아래 Go 전용 설정을 통한 통합 check 연결과 공개 프로젝트 한 개의 실제 설치·실행 검증을 마쳤습니다. 결과 반환·제한 실행·사용자 취소의 범위와 한계는 [실제 통합 명령 검증](https://github.com/hwain-hwang/SENTINEL_GO/blob/main/docs/sentinel-go-native-validation.md#설치된-통합-명령의-go-연결-검증)에 기록했습니다. 설치 플러그인은 아직 활성화하지 않았습니다. 컨테이너 안의 작업 복사본 확인은 같은 사용자 권한의 실행 경계에 있으므로 악의적인 프로젝트가 위조할 수 없는 품질 증거라고 주장하지 않습니다. 모든 실행은 실험 관측이며 정식 운영 허용 조건은 미완료입니다.

## Go 통합 명령의 실험 연결

[native_go.py](../../src/sentinel/native_go.py)가 설치된 Go 설정을 읽고 기존 GoSandbox를 직접 호출합니다. 별도 서버·하위 실행기·변이 엔진을 만들지 않습니다. 기본 check는 계속 거부하며, check --experimental에서만 이 경로를 사용합니다.

1. 일반 설치기에서 protocolVersion=sentinel-go-oci-v1, language=go, version=0.1.0인 묶음을 설치합니다. entrypoint는 실행 파일이 아니라 아래 설정을 담은 JSON입니다. 모든 설치 파일은 소유자 읽기·쓰기만 허용하는 0600 권한입니다.
2. SDK·도구 실행 파일·오프라인 의존성은 기존 내용 설치기로 --tools로 지정한 폴더의 native-content 아래에 미리 준비합니다. 도구 보관 폴더는 Git 밖의 현재 사용자 전용 폴더여야 합니다. 빠진 내용을 자동으로 받거나 원래 언어 저장소에서 대신 찾지 않습니다.
3. workspace의 Go 모듈 config에 검사 설정 파일을 지정합니다. 모듈 전체는 128 MiB 이하의 복사본이어야 하며, .git·.sentinel·링크·특수 파일을 포함하면 거부합니다. 원본 파일 권한을 임의로 바꾸거나 파일을 조용히 제외하지 않습니다.
4. 선택한 모든 도구와 Go 입력을 준비한 뒤 검사를 시작합니다. 모듈의 전체 파일과 설정을 읽기 전용 복사본에 결합하고 원본은 실행 전후 다시 대조합니다. 컨테이너는 이미 로컬에 있는 고정 이미지만 사용하며 자동 다운로드하지 않습니다.

설치 묶음의 entrypoint 설정은 아래 여덟 필드만 허용합니다. 경로 필드 일곱 개는 서로 다른 묶음 내부 파일이며 모두 files의 지문 목록에 있어야 합니다.

|필드|내용|
|---|---|
|schemaVersion|sentinel-go-oci-profile-v1|
|runtimeManifest|고정 Go SDK 파일 목록의 상대 경로|
|artifactManifest|Go 검사 도구 파일 목록의 상대 경로|
|dependenciesManifest|오프라인 의존성 파일 목록의 상대 경로|
|toolchainLock|승인된 Go SDK 잠금 파일의 상대 경로|
|executorLock|승인된 Docker 실행 환경 잠금 파일의 상대 경로|
|imageManifest|고정 이미지 파일 목록 원문의 상대 경로|
|imageConfig|고정 이미지 실행 설정 원문의 상대 경로|

모듈 검사 설정에는 schemaVersion=sentinel-go-check-v1과 sources가 필수입니다. sources는 실제 존재하는 생산용 .go 파일의 상대 경로 1~64개이며, 중복과 _test.go는 허용하지 않습니다. 선택 필드 mutantTimeoutMs는 변이 하나의 컴파일·재실행 제한을 나타내는 정수 1~600000입니다. 생략은 가능하지만 null은 거부합니다.

--timeout-seconds의 기본값은 60초이며 Go 선택 시 최대 900초입니다. 전체 선택 도구의 사전 검증과 읽기 전용 입력 준비는 이 시간에 포함하지 않습니다. 모듈 실행 단계의 입력 재검사·세션 준비·Go 실행은 하나의 마감 시간을 공유합니다. 진행 중인 동기 검증과 별도의 제한된 정리 작업 때문에 명령이 정확히 그 시각에 반환한다고 보장하지는 않습니다.

정상 수집한 Go 종료 코드는 기존 공통 상태로 옮깁니다. 시간 초과·메모리 부족·제거 미확인·입력 불일치는 backendError/6입니다. 사용자 취소와 정리 실패가 겹치면 6을 유지하고 다음 모듈을 시작하지 않습니다. 성공 관측이 있어도 전체 pass와 certified는 false입니다.
