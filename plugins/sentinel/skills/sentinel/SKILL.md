# SENTINEL 검사

에이전트가 검사할 **기능 코드**와 실행할 **테스트 코드**를 고른다. SENTINEL은 코드를 해석하는 LLM 없이 테스트를 실행하고 점수·위치·측정 근거를 반환한다. 지원 언어는 Python·TypeScript·Java다.

확인된 `sentinel` 실행 파일과 프로젝트 루트를 사용한다. 실행기가 없거나 첫 프로젝트라면 [setup.md](references/setup.md)에 따라 필요한 정보와 설치 동의를 확인하고 준비한 뒤 원래 요청을 이어간다. 이미 확인한 정보와 승인받은 설치를 다시 묻지 않는다. Linux·macOS에서는 직접, Windows에서는 WSL로 실행한다. 설명만 요청한 경우에는 설치하지 않는다.

설치·초기 설정만 요청했다면 [start 스킬](../start/SKILL.md)을 따른다. 프로젝트의 `sentinel.config.json`은 기능 코드 폴더와 테스트 폴더를 구분하는 설정이다. 관련 테스트는 에이전트가 프로젝트에서 찾는다.

## 통과할 때까지 수정하라는 요청

"pass 나오게", "통과할 때까지", "기준을 만족하게"는 검사·수정·재검사를 요청한 것이다. 검사만 요청했다면 결과를 설명하고 임의로 코드를 수정하지 않는다.

1. 요청한 기능 범위와 프로젝트의 CRAP·mutation 기준을 확인한다. 새 설정의 기본값은 CRAP 8 이하·mutation 90% 이상이며 기존 설정값은 유지한다.
2. 관련 테스트로 검사한다. `baselineFailed`면 원래 테스트부터 고치고, `qualityFailed`면 점수와 변이 위치를 근거로 요구사항에 맞게 코드·테스트를 보강한다.
3. 같은 범위·기준으로 다시 검사한다. 테스트가 올바른 기대 결과를 확인하는지 검토한다. 통과를 위해 기준을 낮추거나 검사 대상을 제외하거나 테스트를 건너뛰거나 검사기를 개조하지 않는다.
4. 요청한 범위에서 `exitCode: 0`, 모든 `results[].status: passed`, 측정된 CRAP·mutation 판정을 확인할 때까지 반복한다. `noChanges`, 미측정, 도구 오류는 통과가 아니다. 파일·함수를 지정한 요청은 그 범위, 전체 통과 요청은 `--all`로 마지막 검사를 한다.
5. 실제 결과와 검사 범위를 보고한다. 사용자의 중단 요청, 실행 권한·외부 의존성 부족, 요구사항 확인이 필요한 문제로 진행할 수 없으면 막힌 원인과 필요한 입력을 알린다. 성공을 보장하거나 실행하지 않은 결과를 통과로 보고하지 않는다.

## 파일·함수·테스트 선택

아래는 프로젝트 루트에서 실행하는 예시다. 다른 위치에서는 `--project <프로젝트 경로>`를 붙인다. 예시 경로는 실제 프로젝트에 맞게 바꾼다.

```sh
sentinel check --file src/pricing.py --function calculate_discount --tests tests/test_pricing.py
```

1. `sentinel check`: 검사 실행.
2. `--file`: 점수를 측정할 기능 파일. 여러 파일이면 반복한다.
3. `--function`: 해당 파일의 함수 이름. `()` 없이 적고, 생략하면 파일 전체를 검사한다. 함수 선택에는 파일 하나를 지정한다. 같은 이름이 여럿이면 결과의 정확한 함수 식별자를 사용한다.
4. `--tests`: 실행할 테스트 파일. 여러 개면 반복한다. 생략하면 프로젝트에 설정된 테스트 묶음을 실행한다.

출력은 기본적으로 JSON이다. `--format json`은 생략할 수 있고, 텍스트 요약이 필요할 때만 `--format text`를 붙인다.

```sh
# 기능 파일 전체를 두 테스트 파일로 검사한다.
sentinel check --file src/pricing.py --tests tests/test_pricing.py --tests tests/test_boundary.py
# Git 기준 변경된 기능 파일들을 검사한다. 변경 주체가 누구인지는 구분하지 않는다.
sentinel check --changed
# 설정에 포함된 기능 코드 전체를 검사한다.
sentinel check --all
```

`--all`, `--changed`, `--file`은 함께 쓰지 않는다. 파일·테스트 경로는 프로젝트 기준이다. 필요하면 `--module` 또는 `--language`로 범위를 좁힌다. 에이전트는 요청된 작업 안에서 검사 대상을 스스로 선택할 수 있다. 없는 파일·함수, 지원하지 않는 선택은 오류로 처리하며 다른 범위를 검사했다고 대체하지 않는다.

## 테스트 작성과 결과 사용

- 요구사항을 읽고 관련 테스트를 찾는다. 부족하면 정상 입력·경계값·오류 입력의 **기대 결과를 확인하는 테스트**를 작성한다.
- 원본 코드에서 테스트가 먼저 통과해야 한다. 테스트만 수정했어도 같은 `--file`·`--function`을 지정해 재검사한다.
- `details.scope`로 실제 대상과 테스트를 확인한다. `details.crap`은 함수별 점수와 파일별 최댓값(낮을수록 좋음), `details.mutation`은 탐지 개수/전체 변이 수와 탐지율(높을수록 좋음)을 담는다. 기준값도 결과에 함께 나온다.
- `inScope`는 점수 계산에 포함한 변이 수이며 테스트 개수가 아니다. `killed`는 테스트가 발견한 변이 수다. 2개 중 2개를 발견하면 점수는 100%다.
- 명령 결과는 `exitCode`, 검사 범위는 `selection`, 품질 판정은 `results[].status`로 읽는다. `details` 안의 CRAP·mutation `pass`는 해당 범위의 품질 기준 충족 여부다. 종료 0이어도 `noChanges`는 미검사이며, 제공된 `diagnostic`으로 실행 오류를 확인한다.
- 도구가 제공한 복잡도·커버리지·변이 상태·위치는 측정 사실이다. 어떤 코드를 고칠지와 어떤 테스트가 필요한지는 에이전트가 판단한다. 변이 위치를 함수에 연결할 수 없으면 파일 위치만 사용한다.
- `noChanges`는 미검사다. 미측정·오류를 0점이나 100점으로 설명하지 않는다. `selection: partial`은 선택 범위의 결과다. `allConfigured`여도 `results[].status`가 모두 `passed`인지 확인한다. 작업 완료 전 전체 검사가 필요하면 `--all`로 확인한다.
- 검사에는 기본 자동 시간 제한이 없다. 사용자가 중단을 요청하면 취소한다. `backendNotAdmitted` 등 실행 오류는 그대로 보고하고 승인 검사를 우회하지 않는다.
